logging4s

Structured logging for Scala 3 — for any backend, any effect, and any JSON library.

GitHub Maven Central Apache 2.0
Quick start · Loggable · Logging · Backends · Config · Modules · Benchmarks · Migration

You describe how your types render with a Loggable[A] type class, get a Logging[F[_]] for your effect type, and log values directly. Each value is rendered to JSON and attached to the log event as structured data; the message string carries a human-readable rendering of the same values.

The library is a backend-agnostic core plus thin integration modules. The logging backend (logback / log4j2 / slf4j / console), the effect type (cats-effect / ZIO / Kyo / rapid), and the JSON codec (circe / jsoniter / …) are independent modules, each wired in through a given import. core has no dependency on any of them.

Quick start

Pick a backend and an effect runtime (a JSON library is optional — derives Loggable needs none):

libraryDependencies ++= Seq(
  "org.logging4s" %% "logging4s-cats"    % "6.1.0",
  "org.logging4s" %% "logging4s-logback" % "6.1.0"
)
import cats.effect.{IO, IOApp}

import logging4s.core.{Loggable, Logging}
import logging4s.cats.CatsInstances.given        // Delay[IO], cats.Show / data bridges
import logging4s.logback.LogbackInstances.given  // the LoggingFactory

final case class User(id: Int, name: String) derives Loggable

object Main extends IOApp.Simple:
  def run: IO[Unit] =
    for
      log <- Logging.create[IO]("Main")
      _   <- log.info("user created", User(1, "John"))
    yield ()

The logback backend attaches User as a nested JSON object; the message keeps its plain rendering (abridged — LogstashEncoder also writes @timestamp, logger_name, thread_name and the rest of its envelope): 

{"message":"user created: user -> (id -> (1), name -> (John))","user":{"id":1,"name":"John"},"source":"Main.scala:13","level":"INFO"}

The Loggable type class

Everything centers on one type class. A Loggable[A] is required for any value you log:

trait Loggable[A]:
  def key: ValueKey            // the field name the value logs under
  def json(a: A): JsonString   // structured form
  def plain(a: A): PlainString // human-readable form, appended to the message

There are four ways to obtain an instance — derived, fromEncoders, make, and the field-policy builder deriving. Each infers the top-level key from the type name by default, or takes an explicit key as its first argument, consistently across all four: 

Loggable.derived[User]        // key "user"     Loggable.derived[User]("account")
Loggable.fromEncoders[User]   // key "user"     Loggable.fromEncoders[User]("account")
Loggable.make[User](…)        // key "user"     Loggable.make[User]("account")(…)
Loggable.deriving[User]       // key "user"     Loggable.deriving[User]("account")

Derivation

derives Loggable builds both renderings structurally from the fields — the JSON object is assembled by the macro, no JSON library involved. Products key by field name, and a case class without fields renders as {}; sum types delegate to the selected variant, and a case object or parameterless enum case renders as its name. 

final case class Point(x: Int, y: Int) derives Loggable

enum Color derives Loggable:
  case Red, Green, Blue

Recursive types derive too — trees, ASTs, mutually recursive products and recursive enums — and so do generic ones: case class Box[A](value: A) derives Loggable covers every A that has a Loggable. With sumTypeDiscriminator = Some("type") every variant leads with its name — {"type":"Card","last4":"4242"}, and {"type":"Pending"} for a case without fields — so a log query can tell the variants apart.

Derivation reads the first parameter list only — a case class with a second one has no Mirror and does not derive — and renders every field in it, private vals included, as toString does; hide one with a per-field policy.

Named tuples

A named tuple needs no declaration at all — it renders as an object keyed by its own field names, goes through the same keyNameStyle as a derived product, and has no arity limit: 

log.info("order priced", (currency = "EUR", cents = 1999).asLogValue("price"))
// "price":{"currency":"EUR","cents":1999}

From an existing codec

If you already have a JSON codec for A, Loggable.fromEncoders delegates json to it — the log JSON is exactly your codec's output (its field names, its escaping). plain comes from a PlainEncoder (e.g. bridged from cats.Show) when one is in scope; without one it is derived structurally if every field has a Loggable, and otherwise it is the codec's JSON — so the codec alone is always enough. Prefer this when a codec exists. 

given io.circe.Encoder[User] = io.circe.generic.semiauto.deriveEncoder
given Loggable[User]         = Loggable.fromEncoders

By hand, or by adapting another instance

make takes the two renderings directly — json returns a JsonString (JsonString.quoted escapes a string, JsonString(…) is raw), plain a PlainString: 

given Loggable[Money]  = Loggable.make(m => JsonString(m.cents.toString), m => PlainString(s"$$${m.cents / 100.0}"))
given Loggable[UserId] = Loggable[Int].contramap(_.value, "user_id")
val secret             = Loggable[String].redacted()   // always renders "***"

Per-field policies

For derived products, override individual fields with a builder. Selectors are macro-checked field references — not strings, not annotations — so they survive refactors and work on types you don't own. A nested path, a method call or a member that is not a constructor field is a compile error, so a policy never silently applies to nothing: 

given Loggable[Account] =
  Loggable.deriving[Account]
    .hide(_.password)                    // omit
    .mask(_.email)(MaskMode.KeepLast(4)) // partial mask
    .rename(_.id, "account_id")          // custom key
    .unembed(_.address)                  // splice its fields into the parent object
    .derived

MaskMode.Full still reveals the length; for secrets use MaskMode.Fixed("***"), which renders the same mask whatever the value.

Logging

Logging.create returns F[Logging[F]]; the log methods return F[Unit]. There are createTry / createEither / createUnsafe variants for non-effect code. 

for
  log <- Logging.create[IO]("OrderService")
  _   <- log.info("order placed", user, order)          // any number of values
  _   <- log.error("payment failed", throwable, order)  // with a cause
  scoped = log.withContextValues(requestId.asLogValue("request_id"))
  _   <- scoped.info("handled")                         // context attached to every line
yield ()

Any value whose type has a Loggable is passed as it is — user, List(1, 2), Some(order) — and converts under the key of its Loggable, with no implicitConversions import (LoggableValue is an into target); asLogValue("key") picks the key yourself.

An interpolator is available for terser call sites — import logging4s.core.syntax.logging.* and have a given Logging[F] in scope: 

info"order placed: $order"   // == log.info("order placed", order.asLogValue("order"))
HoleKey
an identifier, $orderorder
a selection rooted in one, ${user.id}, ${items.size}the path joined, user_id, items_size
a service selector, ${maybe.get}, ${xs.head}, ${pair._1}the value's Loggable key
any other expression, ${compute()}the value's Loggable key

Values render lazily and every log call checks the level first, so a debug under a logger set to INFO evaluates neither its values (nor an interpolator's expressions) nor their JSON. Every record also carries the call site as a source field — the file name and line, OrderService.scala:42, without the directory or package.

The message must stay static text — it is the aggregation key. log.info(s"user $id created") is a compile error; pass the value as a value, or let the interpolator extract it: 

log.info("user created", id.asLogValue("user_id"))
info"user created $id"

The call site is captured at compile time, so it costs a constant rather than a stack-trace walk. It is the position of the log call: a helper that logs makes every record point at the helper, unless it takes (using Position) itself.

Duplicate keys resolve by specificity: a call-site value overrides a context value with the same key, and a later withContext overrides an earlier one. Only duplicates within a single call are suffixed (k, k_2).

An interpolated Throwable becomes the record's cause, so its stack trace is kept — error"payment failed $e" is log.error("payment failed", e). For a level known only at runtime there is log.log(level, "message", values*). Control characters inside values are escaped in the message text, so a value can never forge a second line in a plain-text log.

A Loggable that throws never costs you the record: the value renders as [failed to render: java.lang.IllegalStateException: …] in both forms, the rest of the record is written, and the logging effect succeeds — the contract SLF4J and log4j2 keep for a parameter whose toString throws.

Fiber-local context

To attach values to everything logged while an effect runs — a request id set by a middleware — without threading a logger through every call, wrap the logger with Logging.contextual and scope the effect. The context lives in the runtime's fiber-local storage: IOLocal for cats-effect, FiberRef for ZIO, Local for Kyo. 

val log = Logging.contextual(base)

ZioLoggingContext.scoped(requestId.asLogValue("request_id")) {  // any ZIO[R, E, A]
  handle(request)                                                // every record inside carries request_id
}

A call-site value wins over the ambient context, which wins over the logger's own withContext. Nested scopes add up — an inner scope that sets a key again overrides it until it ends — the previous context comes back when a scope ends, however it ends (failure, cancellation and interruption included), and a disabled level never reads the fiber-local. The runnable ContextualLoggingExample runs two requests in parallel, each keeping its own request_id.

Testing

Logging.noop[F] discards everything. logging4s.core.testing.RecordingLogging[F] captures each record the way a backend would emit it — context merged, keys normalized and deduplicated — so a test can assert on it without a logging framework: 

val log = RecordingLogging[Try]()
service(log)

log.recorded.map(_.message) shouldEqual Seq("user created")
log.recorded.head.plainOf("user_name") shouldEqual Some("John")
log.recorded.head.jsonOf("user_name") shouldEqual Some("\"John\"")   // valueOf is this JSON form too

Backends

Loggable.json produces a JSON string, but how it reaches the output depends on the backend — the one choice that materially affects the result:

BackendHow structured values are emittedNested JSON?
logbackone logstash marker per record that writes each value as raw JSONYes — genuine nested objects/arrays
log4j2a MapMessage argument (no MDC)Yes with JsonTemplateLayout in object mode
slf4jslf4j 2.x fluent addKeyValueProvider-dependent; typically strings
consolewrites the JSON itself to stdout/stderrYes — no framework needed

The same call comes out as a nested object under logback / log4j2 / console, and as an escaped string under bare slf4j:

{"message":"user created: …","user":{"id":1,"name":"John"}}     // logback / log4j2 / console
{"message":"user created: …","user":"{\"id\":1,\"name\":\"John\"}"} // slf4j — stringly-typed

log4j2 reaches the text and the values through the same resolver, so its event template has to ask for both — a template with only {"$resolver": "message"} emits the values and drops the human-readable text. Use: 

{
  "message": {"$resolver": "message", "stringified": true},
  "data": {"$resolver": "message"}
}

Under logback a value's JSON is rendered only when an encoder writes it, so an appender that prints text alone never pays for it, and %marker in a pattern shows the values as key=json pairs. Under slf4j a value named after an envelope field (level, message, …) is suffixed (level_2), as on every other backend.

We never touch your logback.xml / log4j2.xml: values are only attached to the event and your encoder/layout decides what to render. logging4s-logback also ships an opt-in Logging4sEncoder that writes the JSON itself (no logstash round-trip, no Jackson). It also carries the MDC and slf4j key-value pairs — one without a value as null — and never writes a key twice. Its envelope field names and what it includes are set from the same XML: 

<encoder class="logging4s.logback.Logging4sEncoder">
  <timestampField>time</timestampField>   <!-- also levelField, loggerField, threadField, messageField, stackTraceField -->
  <messageField>msg</messageField>
  <includeThread>false</includeThread>      <!-- also includeMdc, includeKeyValuePairs; all true by default -->
</encoder>

logging4s-console needs no logging framework at all — structured JSON (or colored plain) straight to stdout, ideal for containers. It's configured via HOCON under logging4s.console (override in application.conf or with LOGGING4S_CONSOLE_* env vars): 

logging4s.console {
  level  = "info"    # off | error | warn | info | debug | trace
  format = "json"    # json | plain
  color  = "auto"    # auto (terminal only, also on JDK 22+) | on | off
  stream = "stdout"  # stdout | stderr
  max-stack-trace-lines = -1

  levels {
    "io.netty" = "warn"
    "io.grpc"  = "off"   # silenced entirely
  }
}

auto asks whether the process has a terminal, not the configured stream — with stderr redirected to a file while stdout stays on a terminal, set color = "off". A logger's threshold is resolved once, when it is created, and the default configuration is read once per process; to change levels while running, create loggers under a new given ConsoleConfig. An unrecognised value (level = "warning") makes creating the first console logger throw, naming the setting.

Configuration

Rendering is controlled by a single LoggableEncodingConfig (logging4s.core.config). A default given is provided; override it once, application-wide.

Two values of one type share a key — two timestamps come out as time and time_2; give them names. A Map[String, String] keys as strings, like a List[String], and a search index that maps one field to both an object and an array rejects the second — give a Map its own key.

Compatibility

Every module is built on the 3.9 LTS release. Scala 3 TASTy is backward but not forward compatible, so no release from 4.0 on can be consumed from a 3.3 LTS project — 3.0.x is the line to stay on until your application moves to 3.9.

In exchange, the split that 3.x had is gone: logging4s-kyo and logging4s-rapid used to be pinned to a newer Scala than everything else, and now sit on the same release as core.

Every artifact is compiled with -release 17, so it runs on JDK 17 or later; logging4s-kyo is the exception, below.

Within a major version, binary compatibility is checked by MiMa on every build, and versionScheme := "semver-spec" describes what the artifacts promise.

logging4s-kyo depends on a kyo release candidate (1.0.0-RC7). Until kyo reaches 1.0.0 final, that module sits outside the binary-compatibility promise the other artifacts make. Compiling it also needs JDK 25 — kyo's Frame macro runs inside the compiler and its class files target Java 25, so this is a compile-time requirement, not just a runtime one.

Benchmarks

A JMH harness logs the same mid-size event through every backend into a discarding sink. Every row is logging4s itself on a different backend/encoder — this compares our own backend choices against each other, not logging4s against other logging libraries. Measured on 6.1 as throughput — operations per second, higher is better — and as the bytes allocated per record, with 6.0 alongside (single fork, one machine — rough ballpark, run it on your own hardware):

Configops/sbytes per recordon 6.0
log4j2 + JsonTemplateLayout (nested)~705k~4.2 KB~7.6 KB
console + fromEncoders (jsoniter)~663k~4.3 KB~8.6 KB
logback + Logging4sEncoder~643k~5.3 KB~10.3 KB
console + derives~606k~6.0 KB~11.0 KB
log4j2 (stringified)~510k~3.7 KB~6.1 KB
logback + LogstashEncoder~494k~3.9 KB~6.2 KB

Throughput is rough — error bars of ±5–7% within a run and wider swings between runs, so read it as orders of magnitude. The bytes per record are stable to the byte, and 6.1 allocates 38–49% fewer than 6.0 on every configuration. The encoding path matters as much as the backend: on the same console, fromEncoders with a codec allocates ~28% less than derives. The opt-in Logging4sEncoder runs ~1.3× the standard LogstashEncoder — it builds the JSON in one pass with no Jackson round-trip — though it allocates more, building the line as a String first.

The disabled-level path

A second harness measures what a suppressed record costs — a debug call under a logger set to INFO:

Call shapeops/s on 6.1on 6.0
interpolator, level off~779M~791M
direct call, lazy value, level off~793M~387M
direct call, pre-rendered value, level off (2.x behaviour)~757M~1.5M
interpolator, level on~444k~409k
direct call, level on~476k~406k

In 2.x a suppressed debug still rendered every value to JSON at the call site, so it cost roughly a quarter of an actual log write. 3.0 made values render lazily (~250× cheaper), and the interpolator skipped the call when the level was off. Since 6.1 every call does — a direct call checks the level before it evaluates its arguments, so the three suppressed shapes cost the same. With the level on, the guard costs nothing measurable. The disabled rows are JIT-optimistic in absolute terms — with nothing escaping, escape analysis removes the wrapper allocations outright — so read the orders of magnitude, not the nanoseconds.

Migration

From 6.0 to 6.1

6.1 is binary compatible with 6.0 — MiMa checks every module against it — and call sites compile unchanged, with one deliberate exception (the builder, below). What moves is output, where 6.0 rendered a value in the wrong shape, under a key that did not say what it was, or not at all. 

- "org.logging4s" %% "logging4s-cats" % "6.0.0"
+ "org.logging4s" %% "logging4s-cats" % "6.1.0"
  • Some(x) renders as x — through asLogValue or the interpolator it came out as a one-element array under the plural key ("ints":[1]); it is now "int":1. List and Vector passed directly now compile.
  • An interpolated selection keys by its path — ${user.id} logged under id and is now user_id; service selectors (.get, .head, ._1) keep the value's key.
  • A case class without fields renders as {}, a case object keeps its name, and under sumTypeDiscriminator a variant without fields is {"type":"Pending"}.
  • A Throwable value nests its cause chain, five deep and cycle-safe; the console describes the cause in the message, as every other backend already did.
  • Direct calls check the level before evaluating their arguments — log.debug("x", expensive()) under INFO no longer calls expensive().
  • A Loggable that throws renders a placeholder instead of failing the effect or, with logback, losing the line.
  • The builder rejects a selector that is not a constructor field — .hide(_.someDef) compiled and hid nothing; it is now a compile error.
  • Smaller output fixes — creation-context keys that normalize to one name collapse; slf4j suffixes envelope names; Unit counts as absent; Logging4sEncoder writes a null MDC entry or key-value pair as null (6.0 lost the whole line on a null MDC value).

New in 6.1:

  • No implicitConversions import — LoggableValue is an into target.
  • Fiber-local context for more effects — IOLocalContext.lifted[F] / lift[F](local), and LocalContext for every ZIO[R, E, *] and kyo A < S.
  • More standard instances — java.time calendar types, ZoneId, Date, Duration, URI, URL, InetAddress, Path, Locale, Currency, Try.
  • fromEncoders always compiles with a codec.
  • Logging4sEncoder is configurable from logback.xml.
  • RecordedEvent.jsonOf / plainOf and Logging.emitWith for backends.
  • 38–49% fewer bytes per record on every backend.

From 5.x to 6.0

Call sites compile unchanged. What moves is output in a few places where 5.x lost data or produced lines that could be forged, plus some test-toolkit and SPI signatures. 

- "org.logging4s" %% "logging4s-cats" % "5.0.0"
+ "org.logging4s" %% "logging4s-cats" % "6.0.0"
  • An interpolated Throwable is the cause — error"failed $e" used to attach e as a field and drop the stack trace. The record now gains stack_trace and the e field is gone; pass e.asLogValue("e") to keep it as a value.
  • Control characters in values are escaped in the message text, closing a log-forging hole in plain-text logs. JSON fields are unchanged.
  • RecordingLogging behaves like a backend — RecordedEvent.fields holds the merged, normalized values; valueOf no longer prefers the context over the call site, and keys are normalized.
  • Colliding Map keys are suffixed (null, null_2) instead of written twice; Logging4sEncoder no longer writes an MDC key that a value or the envelope already uses, and LogstashEncoder lines no longer carry "tags":["logging4s.values"].
  • Console color = "auto" stays plain for redirected output on JDK 22+.
  • New members — two LoggableEncodingConfig fields (appended last), Loggable.isAbsent (defaults to false), MaskMode.Fixed. logging4s-cats now depends on cats-effect for IOLocal.

New in 6.0:

  • Fiber-local context via Logging.contextual and IOLocal / FiberRef / kyo Local.
  • log(level, …) for a level chosen at runtime.
  • omitAbsentValues and sumTypeDiscriminator.
  • MaskMode.Fixed, and instances for cats NonEmptyChain / NonEmptySeq / Validated, zio NonEmptyChunk, plus Delay[UIO].

From 4.x to 5.0

5.0 is a correctness release. Everyday call sites are unchanged; what moves is the output in cases where 4.x quietly produced duplicate or wrong data, plus one type-class signature. 

- "org.logging4s" %% "logging4s-cats" % "4.0.0"
+ "org.logging4s" %% "logging4s-cats" % "5.0.0"
  • Field policies compose instead of overwriting each other — .mask(_.password)(…).rename(_.password, "pan") used to silently unmask the value. hide beats mask beats unembed, and FieldPolicy is now a case class of independent settings rather than an enum of mutually exclusive cases.
  • Recursive types derive instead of hanging — recursive products, mutually recursive products and recursive enums all work; field codecs are bound lazily.
  • Duplicate field names are resolved everywhere — a user value named level, two fields that normalize to the same key, a tuple rendered as an object, and unembed colliding with its parent.
  • Context keys are compared after normalization, matching what call-site values already did.
  • Map keys come from the key's JSON form, so keys whose plain rendering collided no longer collapse into one field.
  • Non-finite Float/Double render as JSON null instead of bare NaN, which made the whole record unparseable.
  • Logfmt quotes and escapes values; key-name styles use Locale.ROOT; ZIO Debug plain encoders no longer corrupt values (123 used to render as 2).
  • Loggable.key is a def — override val key = … keeps working.
  • A log message must stay static text — log.info(s"user $id created") no longer compiles; pass id as a value, or use the info"…" interpolator. A message that merely varies, or an interpolation without holes, is still fine.
  • ConsoleConfig holds a Threshold — code that builds it writes Threshold.At(Level.Info) instead of Level.Info, and levelFor became thresholdFor. HOCON is unchanged apart from gaining off.

New in 5.0:

  • Named tuples render as objects keyed by their field names, with no arity limit.
  • off as a console threshold, at the root or per logger.
  • includeValuesInMessage = false keeps the message as bare static text and renders values only into the structured channel.
  • A test toolkit — Logging.noop[F] and logging4s.core.testing.RecordingLogging[F], which records every event for assertions without a logging framework.

From 3.x to 4.0

4.0 breaks in exactly two places: the Scala version the artifacts are built on, and the way Map renders. No call site, type class or given import changes. 

- "org.logging4s" %% "logging4s-cats" % "3.0.0"
+ "org.logging4s" %% "logging4s-cats" % "4.0.0"
  • Your application must be on Scala 3.9 — every module moved from 3.3 LTS to the new 3.9 LTS, and TASTy is not forward compatible. Stay on 3.0.x until you move.
  • Map renders as a JSON object — {"a":1} instead of the old [["a",1]], keyed by the plain form of each key; the plain form follows plainValuesStyle. Restore the old shape with LoggableEncodingConfig(mapAsObject = false).
  • Your own given definitions need Scala 3's new syntax — given L: [A] => (l: Loggable[A]) => Loggable[Wrapper[A]]. A Scala change rather than a logging4s one, but the first thing you hit on 3.9.

Fixed in 4.0:

  • The interpolator rendered eagerly — info"…" built both the JSON and the plain form of every value up front, bypassing the lazy LoggableValue added in 3.0.
  • Field names were not JSON-escaped — a key containing a quote produced invalid JSON.
  • A hole in the middle of a message left a double space.

From 2.x to 3.0

3.0 is a breaking release. Everyday call sites — Logging.create, the per-level methods, withContext, the *Instances.given imports — are unchanged; the breaks are in what you implement and in the shape of the output. 

- "org.logging4s" %% "logging4s-cats" % "2.0.1"
+ "org.logging4s" %% "logging4s-cats" % "3.0.0"
  • Logging[F] has four abstract members instead of twenty-one — implement withContext / emit / enabled / unit; the per-level overloads are final.
  • Level moved to logging4s.core from logging4s.console.
  • LoggableValue is a sealed trait and renders lazily — no copy, no pattern matching; use withKey to rewrite a key.
  • None and Unit render as JSON null instead of an empty string, which used to produce invalid JSON.
  • Records carry a source field — disable with LoggableEncodingConfig(includeSourcePosition = false).
  • Context values merge by key instead of being suffixed.
  • LoggableMapMessage takes Seq[(String, String)] so log4j2 field order follows the call site.

From 1.x to 2.0

2.0.0 is a breaking release, but most call sites need only small edits — Logging.create, the *Instances.given imports, LoggingContext, and the per-level methods are all source-compatible.

1. Bump the version. Coordinates are otherwise identical:

- "org.logging4s" %% "logging4s-cats" % "1.0.1"
+ "org.logging4s" %% "logging4s-cats" % "2.0.0"

2. syntax is now a package — add .all. The extension methods (asLogValue, withKey, Seq.plain) sit behind an aggregator object: 

- import logging4s.core.syntax.*
+ import logging4s.core.syntax.all.*

3. The single make split into four purpose-specific constructors. In 1.x every instance was built with Loggable.make. 2.0 replaces it with four constructors — pick by where the two renderings come from:

1.x2.0Use when
make[A: JsonEncoder: PlainEncoder]("k")Loggable.fromEncoders[A]You have a JSON codec — json is the codec's own output.
n/aderives Loggable / Loggable.derived[A]No codec — JSON assembled structurally by the macro.
n/aLoggable.deriving[A]….derivedDerived, plus per-field policies (hide / mask / rename / unembed).
make[A]("k")(encode, show)Loggable.make[A](json, plain)Fully manual — you write both renderings by hand.
// 1.x — codec-backed make
given Loggable[User] = Loggable.make("user")
// 2.0 — that is exactly fromEncoders (key "user" from the type name; or fromEncoders("user"))
given Loggable[User] = Loggable.fromEncoders

// 1.x — manual make, functions returned String
given Loggable[Money] = Loggable.make("money")(m => m.cents.toString, m => s"$$${m.cents / 100.0}")
// 2.0 — same shape, functions now return the opaque JsonString / PlainString
given Loggable[Money] = Loggable.make(m => JsonString(m.cents.toString), m => PlainString(s"$$${m.cents / 100.0}"))

Every constructor takes the key as an optional first argument, or infers it from the type name.

4. Hand-written instances return opaque types. If you implement Loggable (or JsonEncoder / PlainEncoder) by hand, key / json / plain return ValueKey / JsonString / PlainString instead of raw String — wrap the values. Also rename / contramap / redacted are now final.
